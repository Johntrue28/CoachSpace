# CoachSpace — Decisions

This document records important product and technical decisions.

Statuses:
- **Accepted:** Follow unless the owner explicitly approves a change.
- **Provisional:** Working hypothesis that may change with evidence.
- **To decide:** Not yet resolved.

| ID | Date | Status | Decision | Rationale |
|---|---|---|---|---|
| D-001 | 2026-10-11 | Accepted | Start with one responsive web app; consider a PWA later and native apps only if customers need them. | One codebase, shareable links, and faster iteration. |
| D-002 | 2026-10-11 | Accepted | Use Next.js App Router, TypeScript, and Tailwind CSS; deploy through Vercel connected to GitHub. | A maintainable web stack with preview deployments. |
| D-003 | 2026-10-11 | Accepted | The demo uses fictional data; do not introduce Supabase before the roadmap authorises a real pilot. | Avoid premature backend complexity. |
| D-004 | 2026-10-11 | Accepted | Keep code, UI text, commit messages, and documentation in British English; communicate with the owner in Spanish. | Consistency in the product and clear communication with the owner. |
| D-005 | 2026-10-11 | Provisional | Coaches or academies pay; participants use the product for free. | A coach can invite a whole group, but the buying model must be validated. |
| D-006 | 2026-10-11 | Accepted | The first deliverable is an interactive demo, not a production-ready SaaS. | Validate the problem and solution before investing in backend infrastructure. |
| D-007 | 2026-10-11 | Accepted | Chat is simulated during the demo and must never be represented as real multi-user messaging. | Real messaging requires persistence, identity, and access control. |
| D-008 | 2026-10-11 | Accepted | Keep fictional data in `src/data/`, separate from UI components. | Allows the data source to change later with less UI rework. |
| D-009 | 2026-10-11 | Accepted | Use external video links or embeds during the demo instead of building video hosting. | Reduces storage, bandwidth, and implementation complexity. |
| D-010 | 2026-10-11 | Accepted | Work in small, reviewable increments and preserve working functionality. | Easier to understand, test, and reverse changes. |
| D-011 | 2026-10-11 | Provisional | CoachSpace is the working product name. | Branding and availability have not been fully validated. |
| D-012 | 2026-10-11 | Provisional | Test approximately €9.90/month for an early pilot and €19.90/month as a possible individual-coach price. | Concrete starting hypotheses for customer conversations, not final prices. |
| D-013 | 2026-10-11 | Accepted | Do not add native apps, complex analytics, AI coaching, billing, or advanced academy management without evidence and owner approval. | Keep the initial product focused. |
| D-014 | 2026-10-11 | Provisional | The first target discipline is not chosen yet; research covers tennis, football, basketball, and Pilates coaches. Demo data includes one group from each. | Customer interviews should decide the initial focus. |
| D-015 | 2026-10-11 | Accepted | The current phase is recorded only in `docs/ROADMAP.md`; other documents link to it. | Avoids outdated copies of the project status. |
| D-016 | 2026-10-11 | Accepted | Upgrade Next.js 15.5.4 → 15.5.27 and React 19.1.0 → 19.1.9; pin Node to `22.x`. | 15.5.4 is affected by CVE-2025-66478; pinning Node avoids automatic major upgrades on Vercel. |
| D-017 | 2026-10-11 | To decide | Upgrade to Next.js 16. | Remaining `npm audit` findings (PostCSS bundled inside Next.js 15) are only fixed in Next.js 16, a major version that needs owner approval and testing. Low risk now: the app only processes its own CSS at build time. |
| D-018 | 2026-10-11 | Accepted | `main` is protected by the documented pull-request workflow, not by a GitHub branch protection rule. | Branch protection is not available for private repositories on the GitHub Free plan. Revisit if the plan changes. |
| D-019 | 2026-10-11 | Accepted | Move the start of coach interviews from Phase 0 to Phase 1, before the demo is shown. | Owner prefers to have a more developed product first. Trade-off: less early evidence before building screens. |
| D-020 | 2026-10-11 | To decide | Final public URL and repository name (currently `coach-scpace.vercel.app` and `CoachScpace`, which contain a typo). | Should be fixed before sharing the demo with coaches. Can be changed in Vercel (Settings → Domains) and GitHub (Settings → Repository name). |
| D-021 | 2026-10-11 | Accepted | Prioritise functional coach features over the visual identity during Phase 1. | Owner wants the most complete working demo first; visual polish follows once workflows exist. |
| D-022 | 2026-10-11 | Accepted | The reusable exercise library is the core differentiator: one library per coach, reused across groups, with group-specific instructions and assignment to selected participants. Built before chat. | Saves repeated work for coaches with several groups; distinguishes the product from group messaging apps. To be validated in interviews. |
| D-023 | 2026-10-11 | Accepted | Demo changes (exercises, assignments) are saved in the browser's localStorage and clearly labelled "saved on this device only"; a "Reset demo data" action restores the fictional data. | Makes the demo convincing across reloads without a backend, while staying honest that nothing is shared or stored in the cloud. |
| D-024 | 2026-10-11 | Accepted | Chat messages sent in the demo are kept in memory only (lost on reload), are labelled "Not delivered (demo)", and are not saved to `localStorage`. The demo user is always the coach; one-to-one chats use adult participants only. | Owner instruction: no `localStorage` persistence just for chat. Keeps the simulation honest and avoids implying messages reach anyone. |
| D-025 | 2026-10-11 | Accepted | Announcements live in the demo store with exercises: saved in `localStorage` on this device only, labelled as such and cleared by "Reset demo data" (extends D-023). An announcement targets one group or all groups (`groupId: null`). | Announcements are coach-created content like exercises; the architecture keeps editable demo data in one store. Chat stays in memory only (D-024). |
| D-026 | 2026-10-11 | Accepted | Calendar sessions are generated from each group's weekly slots relative to the real current date, instead of fixed dates. Topics rotate from an anchor date chosen to match the fictional chat. The group's schedule text is derived from the same slots. | The demo must look current whenever it is shown to coaches, and the dashboard, groups and calendar can never disagree. Trade-off: the chat and announcement seed messages keep fixed dates (8–11 October 2026). |
| D-027 | 2026-10-11 | Accepted | Attendance is one record per session (present or absent for every participant of the session's group), saved in the demo store on this device only and cleared by "Reset demo data". Saving requires everyone to be marked; marks can be corrected before and after saving. | Coach-edited data follows D-023. A complete record keeps the summary meaningful. No statistics or history reports (out of scope). |
| D-028 | 2026-10-11 | Accepted | Videos & Exercises completed on top of the existing library: exercises have a required short description; video links are optional but, when added or changed, must be YouTube or Vimeo video links (the demo's existing YouTube search links are kept); one assign screen sets every group at once (whole group, selected participants or not assigned); a participant can belong to several groups (one entry per membership with the same id); `exercisesForParticipant()` lists each exercise once with all the assignments that make it visible. | Covers the gaps listed for Prompt 6 without rebuilding the library or changing the data store. |
| D-029 | 2026-10-11 | Accepted | The participant view is a separate set of routes under `/me`, shown as the fictional participant Jordan Hale (Senior Basketball and Morning Pilates). A "Demo view" switch at the top of every page moves between `/` (coach) and `/me` (participant); the URL decides the view and the navigation. It is labelled as a demo role switch, not a sign-in. | Reuses the existing components without adding role checks to every coach screen, so coach controls cannot leak into the participant view. Real authentication and access control remain Phase 3 work. |
| D-030 | 2026-10-11 | Accepted | Unread counts are calculated from the chat messages and a per-user read state, never stored as numbers on groups. Opening a conversation marks it as read. A user's own messages never count. Initially, a conversation counts as read up to the user's own latest message in it; the demo participant (Jordan Hale) has an explicit starting point in `seedReadState`. The read state is kept in memory only and resets on reload, like the demo messages (D-024). | Badges on the dashboard, the groups list and the chat list always agree with the messages. No messages or activity from other users are simulated. |
| D-031 | 2026-10-11 | Accepted | Calendar changes are stored as exceptions, never as copies of generated sessions: `ScheduleChanges = { overrides: { [sessionId]: changed fields only }, oneOffs: [] }`. The groups' weekly slots stay the only source of recurring sessions. A rescheduled session keeps its original id (`<groupId>-<regular date>`), so attendance, plans and notes stay linked. Cancelled sessions stay visible and marked; they can be restored. One-off ids start with `oo-`. | One source of truth for sessions; the recurring schedule can never be corrupted by a single change, and every screen resolves sessions through the same functions (`src/data/calendar.ts`, `src/data/schedule.ts`). |
| D-032 | 2026-10-11 | Accepted | Session plans and templates share one model (`SessionPlan` with `kind` "template" or "plan"). Items reference library exercises by id, with plan-specific block (warm-up, technical, tactical, cool-down), order, duration and instructions. Creating a plan from a template, adapting a template for a group or saving a plan as a template always makes a copy with new item ids; the source is never modified. | Reuses the existing exercise library instead of a second one; templates stay intact; no extra navigation section (plans live under the library and on each session). |
| D-033 | 2026-10-11 | Accepted | Coach memory is one note per session (what worked, what to improve, what to revisit; up to 280 characters each), linked to the session and its group. It is shown as "From last time" on the group's later sessions and in their plans, newest first, using the sessions' current dates. Notes are private to the coach view. No analytics or scoring. | Keeps the coach's learning next to where the next session is prepared, without a separate tracking subsystem. |
| D-034 | 2026-10-11 | Accepted | Calendar changes, plans and notes are saved with the other coach data in the demo store (`localStorage`, this device only, cleared by "Reset demo data"); all `localStorage` access is isolated in `src/data/persistence.ts`. Chat messages and read state stay in memory only (D-024, D-030). | Changes survive a reload like other coach edits, and a backend can later replace one module instead of the UI. |

## Decision Rules

1. The product owner has final authority over scope, architecture, and priorities.
2. Accepted decisions must not be silently changed.
3. Provisional decisions must be validated before they are treated as settled facts.
4. Before changing a major decision, explain the alternatives, costs, and consequences.
5. After an approved change, update this file and the relevant roadmap, product, or architecture document.
6. Do not record a proposal as accepted without the owner's approval.
